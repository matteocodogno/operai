A new Accounting module keeps the accounting reference data of each legal entity in one place: the ledger accounts, the VAT codes and the monthly average exchange rates. People with Accounting read or manage see an Accounting entry in the menu, with three views (ledger accounts, VAT codes, exchange rates) for each entity they are granted. A manager adds, deactivates and reactivates accounts and VAT codes (an entry is never edited or deleted), fetches or corrects a month's rate, and a reader sees the same lists without the controls. Each entity holds at most 200 ledger accounts and 50 VAT codes, deactivated ones included; since entries are never deleted this is a lifetime limit, and an addition beyond it is refused with `catalog_full`. Refund no longer keeps these lists: it reads them from Accounting each time it needs them, offers only Accounting's active entries, and keeps on each line a copy of the account, VAT code and exchange rate it booked, so a later change in Accounting never alters an approved line or an export already given to the books. When Accounting cannot be read, Refund refuses the change or approval and says so rather than guess; an approved foreign-currency line whose month had no rate gets its rate at the first export. In Refund's Settings the "Accounts and VAT" and "Exchange rates" views are gone (the default account and VAT code of each expense type and the foreign-currency VAT code stay, under "Default classification", with a note that points to Accounting).

Auth declares the `accounting` permissions (`accounting:read` and `accounting:manage`, each limited to an entity if wanted; no separate access permission), grants them to the `admin` role (all entities) and the `accounting` role (WellD CH), derives the Accounting app from them, and accepts the new service scope `accounting.reference.read`. The shell mounts the Accounting remote at `/accounting`. New apps, `accounting-api` (port 8089, own database `accounting`) and `accounting-ui` (port 5183), start at 0.1.0.

Deploy (a person, never an agent; the full runbook is `infra/README.md` § Release runbook, and one push redeploys everything in no fixed order, so each pairing fails closed meanwhile): provision first with `./infra/provision-tool.sh accounting --port 8089`, then set the variables, which are `accounting-api` (`DATABASE_URL`, `ALLOWED_ORIGINS`, `AUTH_*`, `SERVICE_AUDIENCE`, `ACCOUNTING_FX_SOURCE=bazg`), refund-api (`ACCOUNTING_INTERNAL_URL`, now required: without it refund-api does not start and Railway keeps the previous deployment) and the shell (`ACCOUNTING_REMOTE_URL`, `VITE_ACCOUNTING_API_URL`); remove `REFUND_FX_SOURCE` from refund-api, which no longer fetches rates. After the new auth is live, add `accounting.reference.read` to refund-api's entry in auth's `SERVICE_CLIENTS` (auth stops at startup on a scope it does not know, so never before). Until then Accounting answers refund-api 401 and Refund answers 503 `accounting_unavailable`, and approvals stay 409 `accounting_release_pending` until the release below. Then, in this order: `bun run seed:welld-ch --dry-run` and then without it in `accounting-api` (optional, when accounting prefers to type WellD CH's list in the app; the script is in accounting-api's image, so it runs inside the service with `railway ssh`, or from a checkout), and then, from a checkout, `bun run accounting:release --dry-run` and then without it in `refund-api` (it reads Accounting first and exits 2, writing nothing, when it cannot; it takes `--defaults <json>`, and the old `--seed` option is gone). Run the release outside the monthly batch day. `seed:welld-ch` is in accounting-api's Docker image; `accounting:release` is not in refund-api's, which is why it runs from a checkout. refund-api's new migrations (additive, applied by its `preDeploy`) carry what the moved tables kept onto the lines and then drop them; a migration that has been applied is never edited.
