# Security review: legal-entities (OWASP Top 10, 2021), frontier tier

Task T46. Branch `feat/legal-entities`, diff `origin/main...HEAD` (240 files, about 33 000 added lines; head `b061d220`). Read against `spec.md`, `plan.md` (`## Security` and the amendment 2026-11-17 after design, E1 to E14, D1 to D8), the four ADRs `docs/adr/20261117-*`, and `tasks.md` including FU-1 to FU-10. The threat that sets the bar, from the plan (R1): whoever can change an IBAN redirects payments on every document of the suite within 60 seconds.

Method and limits: static review only. `cargo`, `bun`, `pnpm`, `osv-scanner` and `cargo-audit` are not installed on this machine, no server was started and no database touched, so no test was run (the test files were read, not executed) and no advisory database was queried. I ran two small `node` checks (the Content-Type regex, F9) and `grep` over the whole diff. Three things I could not verify offline and flag where they matter: the behaviour of better-auth's 5-minute cookie cache on a revoked session (F2), the SameSite attribute better-auth gives its cookie (left at the library default here; F9), and which Postgres role the auth service connects as in production (F11).

**Verdict: REVIEW REQUIRED** (1 medium, 6 low, 8 info; no critical or high). I found no authorization bypass, injection, secret in the diff, or way for the test-only trigger bypasses to reach production code. The one medium is a design gap the plan itself named (R1): a single valid manager session can change the IBAN with no step-up, no confirmation and no alert to anyone else. It should be decided by the owner before release step 5 (push 2: from then on documents print the registry's values); nothing in it blocks the merge to the branch.

## Findings

### F1 (medium) A04 Insecure Design / A07: an IBAN change has no step-up, no confirmation and no alert; one live manager session redirects payments

- Where: `auth/src/legalEntities/write.routes.ts:249-260` (`authorize`: the grant is the only gate), `:331-358` (save), `:170-218` (`write`: nothing special when `iban` is in `changed`), `auth/src/auth/auth.config.ts:381-388` (session `expiresIn` 7 days, `cookieCache` 5 minutes) and `:446` (JWT `expirationTime: "7d"`); `admin-ui/src/components/LegalEntityForm.tsx`, `LegalEntityFormBar.tsx` and `admin-ui/src/strings/legalEntities.ts` (no confirmation and no warning when the IBAN differs; only the restore has a `ConfirmDialog`, `RestoreDialog.tsx:189`); no use of better-auth's session freshness anywhere in `auth/src`.
- Evidence: the permission check is correct (see "found sound"), so the question is what happens when the person holding it is not who they should be: a stolen laptop, a session token lifted from a browser, a departed employee whose access was removed late. A save needs only a valid session, then changes the IBAN in one POST. Within 30 to 60 seconds every consumer prints it (decision 7), and every offer and contract generated in that time stores it for good (AC-6.4: stored documents and snapshots are never rewritten, `snapshotsUnchanged.test.ts`). Nobody is told: the history page lists who and when, but only to someone who opens it; `audit_log` is read by administrators on request; the plan's own mitigation list (R1) ends with "recommended (owner, out of this spec): a notification to the other managers". The window is also cheap to hide: save, wait 60 s, restore the previous version (no rate limit, F3). The version row and its audit row do record who, so the act is attributable afterwards; the gap is prevention and detection while it happens.
- Impact: direct monetary fraud on every document made while the changed IBAN is live, bounded only by how quickly a human notices. The preconditions are high (a valid manager or administrator session), which is why this is medium and not high.
- Fix (owner: backend-dev for 1 and 2, frontend-dev for 3, wellD owner for 4 and 5):
  1. Alert on every change of the IBAN. This is the owner's recommendation in the section below; build it in this spec's push 2 or the next release, and do not hand `legal-entity:manage` to people other than the `admin` role (release step 5, "Last, grant the managers") until it exists.
  2. Require a fresh sign-in to change the IBAN (not for the other fields). `changedFields` is known inside the transaction, so the check goes in `write()` after `changed` is computed and throws a `Refusal` that the router maps to 403 `recent_sign_in_required`; the session is already on the context:

     ```ts
     // write.routes.ts, in write(), after `const changed = changedFields(before, req.details)`
     if (changed.includes("iban") && Date.now() - req.sessionStartedAt.getTime() > IBAN_SIGN_IN_MAX_AGE_MS) {
       throw new Refusal("reauth"); // -> 403 { code: "recent_sign_in_required" }, no write, no audit row
     }
     // answer(): pass c.get("session")!.createdAt as sessionStartedAt (15 minutes is a reasonable bound)
     ```

     admin-ui then sends the person through the sign-in page and back to the form with the draft kept in memory (`useEntityDrafts` already holds it).
  3. In admin-ui, when the saved IBAN differs from the current one, show a confirmation that names the old and the new value in groups of four and is answered with Cancel focused, as `RestoreDialog` does. This also catches the commonest honest error (a pasted wrong account).
  4. Owner decision: whether an IBAN change by one person should take effect only after a second manager confirms it (dual control), or after a short delay. Either conflicts with AC-1.5 / AC-3.3 (60 seconds) as the owner accepted them, so it is a product decision, not a code defect.
  5. Owner decision: shorten the manager session, or accept 7 days for these routes.

### F2 (low) A01 / A07: save, restore and the history ignore `user.deletedAt`; revocation depends on session deletion alone

- Where: `auth/src/legalEntities/write.routes.ts:249-260` (`authorize` reads `user.entity` only), `history.routes.ts:202-216`, `read.routes.ts:179-186`; `auth/src/admin/users.routes.ts:452-456,549` (soft delete sets `deletedAt`, deletes the sessions, keeps every `UserRole` and `UserDepartment` row); `auth/src/auth/auth.config.ts:384-387` (`cookieCache` enabled, 5 minutes).
- Evidence: after a soft delete the person's roles still resolve (`resolveEffectivePermissions` does not look at `deletedAt`), so `legal-entity:manage` still covers them. What stops them is the deleted session. better-auth's cookie cache lets a signed cache cookie stand in for the session for up to 5 minutes without a database read (library behaviour from its documentation; not verifiable here). Where it applies, a person offboarded by an administrator can still POST for a few minutes. The existing admin routes share the same property (`requireAdmin` also looks only at role rows), but their blast radius is smaller than an IBAN.
- Impact: up to about 5 minutes of write access after an offboarding, only for a soft-deleted holder of the grant, and only if the cache cookie is honoured.
- Fix (owner: backend-dev): the user row is already read, so refuse a deleted user in the three places (and in `/authz/me` if wanted):

  ```ts
  const profile = await db.user.findUnique({ where: { id: userId }, select: { entity: true, deletedAt: true } });
  if (profile === null || profile.deletedAt !== null) return respond(c, 403, FORBIDDEN_BODY);
  ```

  A test: soft-delete a manager, keep a mocked session for them, expect 403 on save, restore and history.

### F3 (low) A04: no throttle on save and restore, and the history has no page size; versions can never be removed

- Where: `auth/src/legalEntities/write.routes.ts:331,360` (no limiter on either POST; `authorize` runs two database reads before the body is looked at), `repo.ts:47-48` (`versionsOf`: "no page, no cap"), `history.routes.ts:235-240` (returns every version, computing `restorable` for each).
- Evidence: the table is Tier 1 (ADR 20261117-legal-entity-registry...): rows cannot be deleted by anything short of a reviewed migration. A script or a stolen session can POST distinct details as fast as the advisory lock allows (each up to 16 KiB). Every one is a permanent row, and `GET .../versions` returns all of them in one response. Besides the storage, this also enables the quick flip-flop of F1. The repo already has `createSlidingWindowRateLimiter` (`auth/src/lib/rateLimiter.ts:74`) used for the `/system` routes.
- Impact: irreversible growth and a slow or oversized history response for the one entity; availability of the history page only (the current-version reads do not scan the history). Needs a manager credential.
- Fix (owner: backend-dev): a per-person limiter on the two POSTs (for example 10 per 10 minutes, one shared key per `userId`, 429 with the shared `tooManyRequests` body), and paging for the history (`limit` default 50, `before` version cursor; admin-ui's `LegalEntityHistory` asks for the next page). Keep the 16 KiB cap.

### F4 (low) A05: one test group commits rows and wipes them with the triggers bypassed, outside any rolled-back transaction, guarded only by "the registry is empty"

- Where: `auth/src/legalEntities/write.routes.test.ts:941-948` (`registryIsEmpty`, `realSuite`), `:954-966` (`wipeRegistry`: `SET LOCAL session_replication_role = replica; DELETE FROM legal_entity_version`, committed), `:124-129` and `import.test.ts:110-115` (`emptyRegistry`: the same, inside `inRolledBackTx`, which is safe). Compare `import.test.ts:72-78` (`assertScratch`), which refuses a database that is not a scratch one.
- Evidence: the task brief and the file headers say the bypass lives only inside rolled-back transactions; that is true for `emptyRegistry` in both files and for `immutability.contract.test.ts`, but not for the "real transactions" group of `write.routes.test.ts`, which commits a version 1 and several saves and then deletes every row for real. Its only guard is that the table is empty when the suite loads. Between release push 1 and the copy (step 3) the production registry IS empty, and the runbook trains operators to prefix commands with `railway run`. A developer who ran `railway run --service auth bun test` in that window would pass the guard, commit fake versions to production, and (the role is a superuser, F11) bypass the triggers to wipe them; if the run died before `afterAll`, the fake version 1 would stay, cannot be deleted, and the import would then report `mismatched`. The auth suite already writes users and roles to whatever database it is pointed at, so the pre-existing risk is of the same kind; what is new is a Tier 1 table that cannot be cleaned afterwards.
- Reachability from production code: none. No production file imports `testDb.ts` (the only mention is a comment in `repo.ts:8`), `routerTable.test.ts` (b) scans every non-test file under `auth/src` for `session_replication_role`, `DISABLE TRIGGER` and raw `UPDATE` / `DELETE` / `TRUNCATE` of the table and finds none, and `import.ts` (the one non-test file that writes) only creates.
- Fix (owner: backend-dev): give the group the same guard as `import.test.ts`: run it only when the host of `DATABASE_URL` is `localhost`, `127.0.0.1`, `host.docker.internal` or the compose service name, never a `*.railway.internal` or `*.rlwy.net` host; skip loudly otherwise. Correct the header comment of `testDb.ts` ("every test that writes runs inside one transaction that is always rolled back") to say the real group is the exception.

### F5 (low) A02 / A04: the copy reads the CRM with auth's own database credentials, "read only" is a session default, and nothing lets the owner confirm the IBAN being copied

- Where: `auth/src/legalEntities/import.ts:208-211` (`openCrmSource`: `default_transaction_read_only: "on"` as a startup parameter), `:499-519` (`runImport`), `:426-441` (audit row: `source.updatedAt` but not who edited the CRM row), `infra/README.md:2471-2476` (`CRM_DATABASE_URL="${DATABASE_URL%/*}/crm"`: auth's URL with the database name swapped, so the same role), `auth/scripts/import-crm-legal-details.ts`.
- Evidence: the script's own safeguards are good (see "found sound"): both URLs from the environment only, an argument is refused and not echoed (exit 64), no value printed, error text reduced to a class name and a code, the read-only setting read back before any read, dry run by default. But `default_transaction_read_only` is a default that any statement can override, and the role is whatever auth runs as on the shared Postgres (F11), which can write to the CRM database. So "read only" holds because the script only ever issues SELECTs, not because the database refuses. Second, the version 1 that becomes the issuer of every document is attributed to "system", and the report prints no value at all, not even a fingerprint: between the dry run and `--apply` the CRM value can change (the freeze is an announcement, plan R4), and the owner cannot compare what is copied with a bank document. The post-copy dry run reports `present`, which proves the copy equals the CRM, not that the CRM was right. Before push 2 the CRM settings (old crm-api) still accept an IBAN edit from anyone with the CRM settings right, so the source can be altered shortly before the copy.
- Impact: low, because the script is operator-run and the operator already holds the database credentials; this is hardening of the one step that takes a financial value from one service's database into a Tier 1 record.
- Fix (owner: devops for 1, backend-dev for 2 and 3):
  1. For the copy window, run it with a role that can only `SELECT` the four columns plus `updatedAt` and `updatedBy` of `entity_profile` in the `crm` database (`CRM_DATABASE_URL` set by hand to that role, as the activities move did), and drop the role afterwards.
  2. Add the CRM row's `updatedBy` (a person id, not a value) to the import audit row's `source`.
  3. Print the last four characters of each IBAN (or its masked form) in the report, in the dry run and the apply, so the owner can check them against the bank's letter before push 2; that stays within "no value printed" in the sense the script uses it, and should be stated in `infra/README.md`.

### F6 (low) A04: the pin-mismatch path clears the shared registry cache on every request that names a different version

- Where: `letterhead-api/api/src/routes/render.rs:222-250` (`issuer_details`: on `pin != details.version` it calls `app.registry.invalidate()` and reads again), `registry/cache.rs:285` (`invalidate`), `auth/src/legalEntities/system.routes.ts:182` and `auth/src/system/systemRateLimits.ts:47` (300 reads per window of 10 minutes per verified service, shared by every replica of `system:letterhead-api`).
- Evidence: the cadence of reads is meant to be one per 30 seconds per process. A caller holding `letterhead:render` (today crm-api only) that sends `legalEntityVersion` different from the current one makes each request drop the entry and call auth (token if needed, then the list), so the cadence becomes the caller's request rate, bounded only by the worker pool's admission (`render.rs` takes the permit before this step). 300 such requests in 10 minutes exhaust the identity's allowance; after that every refresh gets 429, the stale entry is used for at most 60 seconds, then every render answers 503 `legal_entities_unavailable`, including those of well-behaved callers. The same follows from a crm-api bug that sends a wrong pin. It also takes a pin that is a valid positive integer (the validator accepts 1 to `i32::MAX`).
- Impact: availability of document making for all callers, caused by one holder of the render scope or a bug in it; no data exposure.
- Fix (owner: backend-dev, Rust): coalesce forced refreshes, for example at most one per second per process: when the entry was fetched less than a second ago, answer 409 `legal_entity_version_mismatch` at once without calling auth. A matching pin already costs no call.

### F7 (low) A09: the Audit page cannot show the before and after of a legal entity change

- Where: `auth/src/legalEntities/write.routes.ts:209-214` (audit `data` is `{ version, baseVersion, restoredFrom?, changes: { <field>: { before, after } } }`), `admin-ui/src/pages/AuditPage.tsx:221,227` (reads `entry.data?.before` and `entry.data?.after`), `admin-ui/src/strings/audit.ts` (the description now claims "every legal entity change").
- Evidence: by reading (not run): for a `legal_entity.save` row both panes would show "not recorded", because the page looks for `data.before` and `data.after` and these rows carry `data.changes`. AC-2.5 is met in the database (before and after of each changed value are stored in the same transaction as the version), so nothing is lost; but the one place an administrator would look for "what was the IBAN before" shows nothing, and the history page lists field names only (the values are in the version view). It weakens detection of F1.
- Fix (owner: frontend-dev): render `data.changes` for these actions in `AuditPage` (field, before, after), or additionally write `before` and `after` objects in `data`. Keep the IBAN in the page: it is already readable by every signed-in person (AC-3.1), and the page is administrator-only.

### F8 (info) A05: some refusals echo the request path

### F9 (info) A01 / A05: the CSRF posture is sound; two cheap additions would not depend on browser behaviour

- Where: `write.routes.ts:263-279` (the body is parsed only if `Content-Type` matches `^application/(?:[\w.+-]*\+)?json\b`), `auth/src/index.ts:45-53` (CORS allowlist from `ALLOWED_ORIGINS`, credentials on), `admin-ui/src/lib/legalEntitiesApi.ts:261-270` (Bearer token through `apiFetch`, not an ambient cookie).
- Evidence: a cross-site form can only send urlencoded, multipart or `text/plain`, all of which answer 422 before any parse; `application/json` needs a preflight, which only the allowlisted origins pass. The browser UIs authenticate with a token held in memory, so the cookie is not what they rely on. I ran the regex on a few values: `application/json`, `application/json; charset=utf-8` and `application/vnd.api+json` pass; `text/plain`, urlencoded and `application/jsonp` do not; `application/json-foo` does (the `\b`), harmless because it is not a safelisted type and so needs the same preflight. The cookie's SameSite attribute is better-auth's default and is not set in this repository (unverified here).
- Action: as defence in depth, refuse the two POSTs when an `Origin` header is present and not in `ALLOWED_ORIGINS`, and tighten the regex to `^application/json(;|$)`. No change is needed for correctness.

### F11 (info) A05 / A02: the Tier 1 guarantee ends at the database role; accepted by the ADR, restated here because the target is an IBAN

- Where: `auth/prisma/migrations/20261117100000_legal_entities/migration.sql` (row trigger for UPDATE and DELETE, statement trigger for TRUNCATE, CHECKs), `docs/adr/20261117-legal-entity-registry-in-auth-...md` lines 34, 117, 128, 134.
- Evidence: the triggers and the CHECKs are correct and cover what they claim (`INSERT ... ON CONFLICT DO UPDATE` fires the update trigger; the import row is pinned to version 1 by the system; a restore points back). They stop nothing done by the table's owner or a superuser (`DISABLE TRIGGER`, `session_replication_role`, `DROP TABLE`, an `ALTER COLUMN TYPE` rewrite). Auth's runtime role and the migration role are the same here, and the runbook's database is shared (F5). So anyone who can run arbitrary SQL as auth, through an injection bug elsewhere in auth or a leaked connection string, can rewrite history. The ADR states this limit and treats it as accepted (Risks). I found no SQL injection in the feature: every query in `repo.ts`, `import.ts` and the routes is a Prisma tagged template or the typed client; `$executeRawUnsafe` appears only in tests and in `testDb.ts`. `createdByUserId` and `createdByName` are personal data that cannot be erased through the service (ADR, "triggers" and "GDPR" lines); an erasure request needs an owner decision.
- Action: none for this release. If the owner wants the guarantee to survive a compromised auth process, give the runtime a role without ownership of the table and keep the migration role separate (the letterhead review's F-list made the same remark).

## What was checked and found sound

Included so the next reviewer does not redo it.

- **Save and restore authorization (`write.routes.ts`).** The order is 401, 403 (no grant covering any entity, constant body, also for an unknown entity name, so a person without a grant learns nothing), 404 `unknown_legal_entity` (constant), 403 (a grant that does not cover this entity), 413, 422 shape, 422 rules, then the transaction. The coverage is `entityGrantFor` through `coveredEntities` (`coverage.ts:22-30`): an unconditioned grant covers both entities, `{key:"entity", match:"user"}` covers the holder's own entity attribute only, a user with no entity attribute is covered only by an unconditioned grant, and any other condition (ownership, another key or match) contributes nothing (`resolver.ts` `grantKind`/`entityGrantFor`, fail closed). The user's `entity` attribute is changed only by `PATCH /admin/users/:id` (`requireAdmin`, audited; `ENTITY_VALUES` is now the same list); no self-service route and no better-auth additional field can set it. The only default holder is the `admin` role (`seedLegalEntityGrants`, unconditioned, idempotent); the catalog declares the entity condition only (`catalogs/admin.ts`).
- **Concurrency and atomicity.** `pg_advisory_xact_lock(hashtext('legal_entity:<entity>'))` is taken first inside `withAudit`; the current version is read after the lock at read-committed, so two saves on one base cannot both pass; the key is the one the import script uses (the test reads both sources). The version row and the audit row are written in one transaction; the "same" outcome writes neither. A conflict, a not-moved entity and any error roll back with no audit row. `baseVersion` is bounded to an int4. A stored version is read outside the transaction for a restore, which is safe because versions never change.
- **Body and input.** 16 KiB cap before any parse, declared and streamed (`boundedBody.ts`); `z.strictObject` at every level, so `__proto__` and any extra member are 422; address arrays capped at 16; everything normalised (NFC, trim, IBAN whitespace and case) and judged after normalisation, and the stored value is `normalise(details)`, never the raw body. Control characters, line breaks and lone surrogates are refused before they can reach Postgres (which cannot store NUL). The IBAN is format-checked and mod-97 checked. Unicode format characters (bidi controls) are not refused, which matters only to a person who may already change the values.
- **No echo, constant 500.** `answer()` returns a constant 500 body and logs only an error class and a code (`safeErrorText`); no 4xx body repeats a submitted value (tests assert the sentinel strings and the IBAN do not appear). Errors thrown outside that try block (the permission read, the restore's stored-version read) reach `onError`, which logs the error object but whose queries carry only user ids, entity names and version numbers as parameters, and answers a generic 500 in production.
- **Reads.** Any signed-in person reads both entities including the IBAN (owner decision AC-3.1; not new exposure beyond what every offer prints); `Cache-Control: no-store` on every answer including the 401, 403 and 404; auth attached per exact path, so the history and write routes never inherit the person read's looser rule; `manageable` is registered before `{entity}` and answers about the caller only; the history needs a covering grant (any covered entity reads either history, AC-4.3) and answers 403 before 404. `createdBy` (id and name) goes to managers only.
- **`GET /system/legal-entities`.** The verifier (`system.routes.ts:137-165`) is line for line the one of `POST /system/users/contact`: RS256 pinned, issuer, `aud = SERVICE_AUDIENCE` (which must differ from `AUTH_AUDIENCE`, `lib/env.ts:176`, so a person's token fails), required `exp sub aud iss`, `sub` starting `system:` with something after it, the scope matched as a whole word, token length capped. Every failure gives the same frozen 401 body; the credential is verified before any count; an invalid one spends the source address's shared count, a valid one the service's own allowance; the entity name is looked at only afterwards; `manageable` under `/system` is the same 404 as any unknown name. The log line names the caller and nothing else. The scope `legal-entities:read` is granted only by `SERVICE_CLIENTS` configuration (crm-api, letterhead-api); a read-only scope over data every person can already read.
- **Immutability.** The triggers and CHECKs are as the plan lists; `routerTable.test.ts` reads the real route table (only GET and POST under `/legal-entities` and `/system/legal-entities`, the two POSTs are the save and the restore, no `ALL`), proves PUT, PATCH and DELETE answer 404 for an administrator, and statically scans `auth/src` (excluding tests) for mutating Prisma calls, raw UPDATE, DELETE and TRUNCATE, trigger switches and `session_replication_role`, with positive controls. It does not scan `auth/scripts/`, which holds only the thin import entry point and an e2e fixture.
- **`/authz/me` and admin-ui.** The derived `admin` entry (`authz.routes.ts`, after the `access` filter) is read by the shell's tool guard and admin-ui's `AdminShell` only; I found no server-side use of `apps` as an authorization decision, and `/authz/resolve`, `/authz/app-access-check` and the directory filter do not derive it. Every admin API (`roles`, `users`, `departments`, `userAddress`, `audit`, `catalog`, `invitations`, `accessRequests`) is still behind `requireAdmin`, which checks direct `admin` role membership. `AdminShell.gateFor` fails closed (pending and failed `manageable` never open a page; a manager-only person is kept off the admin sections); all admin section paths are under the segments the shell classifies as admin (`/users/invitations` and `/users/access-requests` included), so no admin page mounts for a manager-only person. `validateLegalEntitiesSearch` keeps only the closed values and the `beforeLoad` rewrites the address, so a bad `entity`, `view` or `version` never reaches the page. Drafts are held in memory only (no web storage).
- **The copy script.** Credentials come from the environment only and a second argument of any shape is refused without being printed; `crm_not_read_only`, `crm_entity_profile_absent` and `crm_legal_columns_absent` stop before any read; `crm_row_unreadable`, `registry_not_contiguous` and `import_readback_mismatch` carry no value; the report names entities, categories, field names, reasons, line numbers and limits; it inserts only version 1 and only where none exists, under the entity's lock with its audit row in one transaction, and reads the row back; it never overwrites. The local `mise` task builds both URLs from `POSTGRES_*` and ignores any exported production variable. The scratch-database guard of its test (`CRM_TEST_DATABASE_URL`) refuses `crm`, `auth`, `operai_auth` and `postgres`. See F5 and F12 for the remaining points.
- **letterhead-api.** Service-token client: no redirect (`Policy::none()`), the body of a failed exchange is never read, token answer capped at 16 KiB and registry answer at 64 KiB by announced length and by bytes read, the secret in no log, error or `Debug`, startup validation without repeating the value, the secret only in the supervisor (`env_clear` for workers, `pool/mod.rs:198`); a 401 drops that token and retries once. Cache: one entry stamped with the send time on a monotonic clock, 30 s fresh, stale for at most 60 s only when a refresh fails, otherwise 503 `legal_entities_unavailable` with `Retry-After: 5`; single flight, 5 s bound, a late refresh not cached after `invalidate`. The mark mode cannot reach a document: `Job::encode` and `decode_job` both refuse `mark_missing` on anything but a preview, only `sample_job` of the configurator sets it, the header member is omitted otherwise, and the replaced template text is a pair of constants (no request or registry text enters the Typst source). `legalEntityVersion` is accepted only in content version 2 (a v1 request carrying it is an unknown member), must be a positive integer, and a mismatch after one refresh is a 409 with the current version only. The preview never reaches a document and degrades to "unavailable" with every placeholder marked.
- **crm-api.** The registry client has the same cache rule, `redirect: "error"`, a 5 s bound, a 64 KiB cap and logs statuses and error names only; no service client means every read fails closed (503). `withIssuerPin` retries once, then the client's own 503. All guards on the offer, draft and template routes are unchanged (`generating`, `reading`, `dealScope`, `assertInScope`), with `legalEntitiesRetryAfter` added. The legal fields are gone from `GET` and `PUT /entity-profiles`; the four legacy keys are accepted as `z.unknown()` and dropped (nothing reaches an insert), any other key is still refused by `.strict()`, the body cap (`smallBody`) still applies, and the migration only adds two defaults. New refusals carry the entity and the closed `missing` list, never a value. Classic PDFs draw issuer text through `winAnsi`.
- **Front ends.** No `dangerouslySetInnerHTML`, `innerHTML`, `eval` or `window.open` in any added source file. The `/admin/legal-entities?entity=` links are built from the closed `Entity` union with `encodeURIComponent` and a fixed path (`LegalEntityNotice.tsx:10`, `LegalEntitySettingsNote.tsx:7`, `PreviewPane.tsx:26`). `useCanManageLegalEntity` (both copies) is keyed by the session's user id, drops a failed answer, and returns false while pending, on any error, on a non-answer, and when `getAuthBaseUrl` is missing (letterheads-ui reads it through a cast inside the ask, so a missing export fails closed: FU-10 is a typing cleanup, not a risk). Registry values and `missing` entries render as React text; `legalDetailsInWords` shows an unknown entry as received, as text, and guards with `Object.hasOwn`. The API client of admin-ui parses every answer against the contract and never branches on prose.
- **Secrets scan of the diff.** I searched every added line for credential shapes (connection strings with a password, private keys, `AKIA`, `ghp_`, `sk-`, `xox`, generic secret and token assignments). Hits are test sentinels, a deliberately fake connection string in a test of the refusal of arguments, `replace-with-...` placeholders, the dev default of F10, and `${{shared.*}}` references in the env-doctor templates. The IBANs in fixtures, goldens and tests are the public ISO and SIX example numbers (CH93 0076 2011 6238 5295 7, IT60 X054 2811 1010 0000 0123 456 and the like); VAT numbers and company names in the fixtures are synthetic.

## Recommendation to the owner (outside this spec): tell the other managers when an IBAN changes

The plan (R1) and the ADR suggest it and leave it out of scope. I recommend it, and I recommend that it ships no later than the first day a person other than the `admin` role holds `legal-entity:manage` (release step 5, "Last, grant the managers"); it is the only control that works after a valid session has been abused.

- Trigger: a save or a restore whose `changedFields` contains `iban`. Consider `legalName` and `vatNumber` too, since a changed issuer identity is also fraud; leave address and contacts out to keep the signal rare.
- Recipients: everyone whose grant covers that entity (administrators included), the person who made the change (as a receipt), and one address outside the suite, configured in auth (for example `LEGAL_ENTITY_ALERT_EMAIL`, the finance owner's mailbox), so that an attacker who removes people from roles in the suite cannot silence the alert.
- Content: entity, version number, who, when, which fields, the last four characters of the old and the new IBAN (never the full value in an email), and a link to the history page where Restore is one click away.
- Mechanism: auth already mints its own notify credential in process and sends invitation emails (`lib/notify.ts`, ADR 20261013-auth-mints-own-service-credential-in-process, ADR 20260714-notify-api-email-channel-service-trust), so no new service dependency. Send after the transaction commits; a delivery failure must not fail the save, but must leave a trace (an audit row `legal_entity.notice_failed` and a log line), and a retry (a small outbox row written in the same transaction as the version is the robust form) so a mail outage on the day of an attack does not hide it.
- Test: a save with an IBAN change sends one notice to each recipient and none for a change of the contacts line; a no-op save sends nothing; a failed send leaves the version saved and a failure row.
- Together with F1 items 2 and 3 this makes an IBAN change need a recent sign-in, an explicit confirmation by the person, and a notice to others; dual control (F1 item 4) would be the next step if the owner wants prevention and not only detection.
