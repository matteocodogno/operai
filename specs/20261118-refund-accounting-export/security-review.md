## Surfaces checked, no finding

1. **Export endpoints** (export.routes.ts, export.repo.ts): JWT + authz middleware on both paths; capability `request:review` AND scope global or `welld_ch` (`scope === null` is refused); the check runs BEFORE the batch lookup, so no batch-existence oracle; 404/409 for unknown/discarded; 409 blocked returns no file; the log row is written before the body and a failed write returns 500 with no file; filename built from the cutoff date and a sanitised batch id (`[^A-Za-z0-9_-]` replaced), no PII; `Content-Type`, `attachment`, `nosniff`, `no-store` set; CORS exposes only the three download headers; error logs carry the batch id and error name only, and only after the batch is found (no log injection).
2. **Outbound FX** (bazgSource.ts): constant https host, URL built from a validated `YYYY-MM` only (`REFUND_FX_SOURCE` is an enum `bazg|off`, never a URL), `redirect: "error"`, 5 s per call plus the 10 s trigger budget on one signal, `Content-Length` shortcut plus a streamed cap of 512 KiB applied to the decoded body (so a compressed bomb is cut too), failures returned as codes with no body or URL text. Request volume is bounded: 6 months per trigger, 15 min throttle per month, in-flight dedupe, and `off` mode for offline use. A GET (the export summary) can trigger the fetch for any in-scope reviewer, which is bounded by the same limits.
3. **XML**: no XML library, so no entity resolution; DOCTYPE, ENTITY and CDATA refused before any read; comments stripped then rechecked; echo month must equal the requested month; BigInt maths bounded by `MAX_KURS_CHARS`. No ReDoS shape found (lazy quantifiers on a document capped at 512 KiB).
4. **Classification PUT**: body limit 4 KiB, ids max 64; `FOR UPDATE` on the request row inside the transaction and status read from the locked row; permission chosen by status (`set-approved-total` while submitted, `reclassify` when approved, paid refused, DB trigger behind it); the line must belong to the request; account and VAT code must exist for `welld_ch` and be active; only the named columns are written; one `line_classified` audit row per change. All raw SQL is tagged-template bound (no `$queryRawUnsafe`). IDOR across requests is closed by the lookup within the locked request; the cross-entity gap is S-01.
5. **Management routes**: `/accounting/ledger-accounts/*`, `/accounting/vat-codes/*`, `/accounting/expense-type-defaults/*`, `/accounting/foreign-currency-vat-code`, `/exchange-rates/*`: JWT, authz, `settings:read` for GET/HEAD and `settings:manage` for every other method (a method with no route still hits the gate), 4 KiB body limits, regexes on account number (3-6 digits), VAT code, rate (`^\d{1,3}(\.\d{1,6})?$`, 0 < rate < 1000), month `YYYY-MM`, max 24 months per fetch body; actor taken from the JWT; corrections append-only with history; future months refused.
6. **auth grants**: `reclassify` declared once, `entity` condition only; `accounting` entity-conditioned, `refund-admin` global, `admin` mirrors `approve`, `employee` none; seed idempotent (parity tests exist). The only concern is S-02.
7. **Release script**: reads local paths only, offsets validated (email shape, year, 1-99999, duplicates), refuses a pair that already has numbers, single transaction with an advisory lock, `--dry-run` rolls back; system actors are named constants. Seed JSON and fixtures contain no new personal data (the two names in fixtures already exist on main). Concerns: S-03, S-04.
8. **refund-ui**: no `dangerouslySetInnerHTML`/`innerHTML`/web storage in the diff; the download uses the in-memory bearer through `apiFetch`, builds the filename client-side, creates and revokes an object URL; blocked-summary parsing validates every field's type; no keys or secrets in the UI diff; client route guards are UX only and the server enforces every permission.
9. **Dependencies (A06)**: no new runtime dependency in refund-api/package.json (one script added); the gates' dependency audit is the enforcement point.

### Bypass checks

- **Pre-approval path (`set-approved-total`)**: the PUT does not trust the grant name; while the request is `submitted` the self-restriction is read from the `approve` grant, so an owner barred from approving cannot classify their own submitted request even though `set-approved-total` itself is unconditioned (by design of the earlier self-approval spec). Mixed-scope: the line-level check uses the `set-approved-total` scope in that state, so a `welld_it` caller cannot touch a CH line there either.
- **Status races**: both the status and the grant are chosen on the row locked by `SELECT ... FOR UPDATE`; approve, pay and withdraw serialize on the same row. A paid request is still refused by the route and by the DB trigger.
- **Withdraw-clears-overrides** (lifecycle.repo.ts): applies only to a `submitted` request inside the withdraw transaction, and only to the owner's own withdrawal. It never touches an approved or numbered line, writes one audited `line_classified` row (cause `withdrawn`) per cleared line, and writes nothing that grants anyone new rights. It is not a way to change an approved booking. No issue.
- **Release script**: runs as the named system actor, uses defaults only, takes no caller input beyond operator-supplied local files, and has no self-approval relevance. The new masking, worktree warning and ignore rules do not widen anything. No issue.
- **Approve path**: unchanged in this round; the owner is blocked by the existing self-approval control.

### Residual notes (info, no action required for release)

- R-1: an owner who holds `set-approved-total` and/or `reclassify` but NO `approve` grant (a hand-built role) is not restricted by S-02, because the restriction is derived from `approve`/`reclassify` conditions on the caller. The seeded `accounting`, `refund-admin` and `admin` roles carry both grants, so the seeded configuration is covered. Keep it in mind when creating custom roles.
- R-2: approval by an approver whose scope covers only one entity still numbers and freezes the other entity's lines of a mixed request with the live defaults (request-level approve semantics from the earlier ADR; no value chosen by the approver). That is the pre-existing approval model, not part of this change.

No new issue was introduced by the fix.
