# Security review (OWASP Top 10): Accounting module

Task T47. Branch `feat/accounting-module` against `feat/refund-accounting-spec` (356 files; the accounting-api service, accounting-ui, the refund-api move, the auth catalog, shell, infra). Read-only static review: grep, `git diff`, `git log`, file reads. No test suite, no service, no network, nothing committed.
Reviewer: owasp-reviewer, standard tier, as `plan.md` "## Security" (flag YES) asks. Date: 2026-11-19. Stacks: Bun + Hono + Prisma (accounting-api, refund-api), React (accounting-ui, refund-ui, shell). No JPA/jOOQ rules apply.

## Verdict: REVIEW REQUIRED (0 critical, 0 high, 1 medium, 6 low, 6 info)

**The escalation trigger of the plan does NOT fire; no frontier-tier re-review is needed.**
- No system route is reachable by a principal outside `SYSTEM_READERS = ["system:refund-api"]`: RS256 pinned, issuer pinned, `aud = SERVICE_AUDIENCE` (startup refuses it equal to `AUTH_AUDIENCE`), `exp`/`sub`/`aud`/`iss` required, the scope matched as a whole word, the `sub` on the allow-list, one frozen 401 body for every failure, GET only (accounting-api/src/auth/systemAuth.middleware.ts:77-96, src/system/readers.ts:15-29).
- No user route reads or writes another entity's data: every `/v1/entities/{entity}/...` path goes through `jwtMiddleware`, `authzMiddleware`, then `requireEntityAccess`, in that order, before any body is read (catalog.routes.ts:112-123, rates.routes.ts:141-151, coverage.ts:128-150). `matrix.test.ts` reads `app.routes` and fails when a route is not in its table, and asserts that no `/v1/entities` route exists for a method the gate does not check.

The one medium is a design gap between a producer and a consumer limit, not an access-control hole (F-01). None of the findings exposes data to an outsider or changes a money figure. All six closed findings of 20261118 (S-01 to S-06) still hold (see the regression table).

## What a raw SQL write can still do

- **accounting-api (five append-only tables).** Row triggers raise on UPDATE and DELETE, CHECKs bound every value (number and code formats, rate 0 to 10000 bp and 0 to 1e9 micros, own currency refused, origin versus fetch columns, status-row entity must match its entry by trigger). A raw writer with INSERT can still: add an account, VAT code, status row, fetched rate (once per entity, currency, month, by the partial unique index), correction or attempt row with any actor and any `createdAt` (a far-future `createdAt` would make an inserted correction the one in effect until a manager's next correction, which the code stamps strictly after the latest row); flip a status by inserting a row. With the application's role (the shared owner user) it can also `TRUNCATE`, `DISABLE TRIGGER`, `DROP`, or use `session_replication_role` (F-06). Nothing checks `exchange_rate_fetch_attempt.trigger` or `.outcome` values (text, no CHECK) or its month's day.
- **refund-api (`refund_line` copies).** `refund_line_accounting_guard` v2 keeps the five receipt columns immutable once numbered, locks the six copy columns (account number and name, VAT code and rate, both is-default flags) once the line is numbered AND its request is `paid`, and makes the three `fx*` columns write-once (null to set allowed, set to anything else refused), with CHECKs: the rate month equals the expense month, foreign and WellD CH only, all-or-none, range. A raw writer can still: set any copy on a numbered, not yet paid line (no foreign key to Accounting, no format check on the copies; that is the reclassify path), set a rate on a pending line (range-checked only), change `approvedTotalCents`, `currency`, `date`, `rejectionReason` after numbering or payment (never guarded, unchanged from 20261118), and the same owner-role bypasses as above. The two copy-history tables and `refund_batch_export` are trigger-protected in the same way.

## Checked clean (surfaces with no finding)

1. **accounting-api user routes** (`/v1/me`, catalog, rates): JWT then live `GET /authz/resolve` (fail closed 503, no stale entry, 30 s cache keyed by sub and `perm_epoch`); entity coverage from the resolved grants only (`read` is read union manage, `ownership` or any unknown condition covers nothing, stricter than auth where they differ, parity vectors shared with auth); order 403 (no coverage at all) then 404 (unknown or uncovered entity, one body) then 403 manage-required, before any body is read; actor from the JWT; extra body keys ignored, entity from the path only; no PUT, PATCH or DELETE route on entries (the correction PUT is the one PUT, manage-gated, month completed, currency convertible, `0 < rate < 1000`); 4 KiB body cap (global, 413 Problem); regexes are unambiguous (no nested quantifier) and run after trim; `upperCaseCode` is ASCII-only (no `ß`). Trailing slash, HEAD, encoded NUL and `__proto__` entity paths are covered by the matrix.
2. **CORS**: `ALLOWED_ORIGINS` from the environment, a wildcard fails startup, `credentials: true` with an explicit list, methods `GET POST PUT OPTIONS`; production template names the shell origin only.
3. **Problem JSON / AC-6.10**: 500 detail is the fixed sentence outside `development`, and the Dockerfile and the compose service set `NODE_ENV=production`; 4xx details are fixed sentences or zod messages without the input value; the system 401 is one body per path; refund-api's 503 `accounting_unavailable` is generic with `instance` = the route pattern, no id, host or URL; `AccountingUnavailableError` has a fixed message and only `kind` and the operation name are logged. The app's own 404 echoes method and path as JSON only.
4. **`/system/v1/*`**: see the verdict.
